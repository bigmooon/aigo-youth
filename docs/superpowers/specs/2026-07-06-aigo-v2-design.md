# aigo v2 설계 스펙 — 임대차 계약서 위험 조항 탐지 시스템

- 작성일: 2026-07-06
- 상태: 사용자 리뷰 대기
- 전신: [aigo-ai](https://github.com/SKN24-Chatbot/aigo-ai) (SK네트웍스 Family AI 캠프 24기 3차 팀 프로젝트 "아이고~~ 청년!") — v2는 개인 프로젝트로 재설계하며, README에 v1 팀 크레딧을 명기한다. v1 코드 재사용 범위는 라이선스 확인 후 확정.

## 1. 문제 정의

**임대차 제도는 계약 당사자보다 빨리 바뀐다.** 임대차법 개정, 전세대출·보증보험 요건 변경, 새로운 사기 수법이 계속 등장하지만, 청년은 인생 첫 임대차 계약을 몇 년에 한 번 경험한다. 개인이 아무리 성실해도 변화 속도를 따라갈 수 없는 구조이며, 부모 세대의 경험은 과거 제도 기준이라 오히려 위험할 수 있다. 전세사기 피해자의 75.1%가 20~30대(국토교통부, 2025.05)이고, 주요 원인은 계약 전 위험 조항 미인지다.

핵심 통찰: 임차인은 **뭐가 위험한지 몰라서 질문 자체를 못 한다.** 따라서 "물어보면 답하는 챗봇"(v1)이 아니라 "안 물어봐도 전체를 스캔해서 근거를 찾아주는 시스템"(v2)이 맞는 형태다.

## 2. 포지셔닝: v1 → v2 델타

| | v1 (팀) | v2 (개인) |
|---|---|---|
| 입력 | 사용자가 특약을 타이핑 | 계약서 파일 업로드 (PDF 우선) |
| 동작 | Q&A | 조항 자동 분해 → 조항별 근거 매칭 → 리포트 |
| 출력 | 대화 답변 | 발견 유형 리포트 + 후속 Q&A |
| 품질 관리 | 평가 노트북 | 골든셋 기반 자동 평가 + CI 회귀 |
| 정체성 | RAG 챗봇 | 정확도를 측정하는 탐지 시스템 |

스코프 아웃: 주소 기반 위험도 조회(공공서비스 존재), 등기부등본 분석, 사진 OCR(P4 이후), 모바일 앱, 대출·보증보험 규제 탐지(체크리스트 콘텐츠로만 제공), 법률 자문성 판정.

## 3. 판정이 아닌 근거 제시 (법적 리스크 대응)

"위험/주의/무난" 등급 판정은 비변호사의 법률 사무(변호사법 제109조) 소지 및 오판 책임 문제가 있어 채택하지 않는다. 시스템은 조항별로 **검증 가능한 사실**만 제시한다:

| 발견 유형 | 의미 | 근거 |
|---|---|---|
| ⚖️ 법령과 다름 | 강행규정 등 법령 조문과 상이한 내용 | 법령 조문 ID |
| 📚 분쟁 전례 있음 | 유사 문구가 다투어진 판례·조정 사례 존재 | 판례 번호 / 사례집 사례 ID |
| 📋 표준계약서와 상이 | 국토부 표준임대차계약서에 없거나 다른 특약 | 표준계약서 조항 |
| ✅ 특이사항 없음 | 발견된 근거 없음 | — |

"위험하다"는 시스템이 말하지 않는다. 법령·판례를 옆에 놓아주면 위험함은 사용자가 판단한다. 후속 Q&A도 동일 원칙(결론 대신 근거)으로 프롬프트를 설계한다. 모든 화면에 "법률 자문이 아닌 정보 제공" 고지(v1 유지). 리포트에 분석 기준일("YYYY-MM-DD 기준 법령 데이터")을 명시한다.

부수 효과: 라벨의 ground truth가 "위험 등급(주관)"이 아니라 "조문 상충 여부(객관)"가 되어 평가가 방어 가능해진다.

## 4. 사용자 플로우

1. 계약서 PDF 업로드
2. 리포트: 조항별 발견 유형 + 근거 인용(v1의 결정론적 인용 링크 방식 유지) + 계약 전 확인 체크리스트(대출·보증보험 등 탐지 범위 밖 항목 포함)
3. 조항 클릭 → 챗봇 후속 질문 (v1 Q&A 파이프라인 재활용)

## 5. 아키텍처

기존 LangGraph 파이프라인을 확장. 탐지 그래프(신규)와 Q&A 그래프(v1)가 리트리벌·인용 노드를 공유한다.

```
업로드 → 텍스트 추출(PDF) → 조항 분해(segmentation)
  → [조항별 병렬] 카테고리 분류 → 근거 리트리벌(Qdrant) → 발견 유형 판정(근거 존재 여부 기반)
  → 인용 검증 → 리포트 생성
```

- 스택 유지: Python, LangGraph, Qdrant, kure-v1 임베딩, 국가법령정보 Open API, EXAONE/vLLM 옵션.
- 추가: PDF 파싱 라이브러리, pytest, GitHub Actions. UI는 Streamlit 유지(P3까지).
- 위험 카테고리 체계(taxonomy): 보증금 반환 방해, 원상복구 과잉 부담, 수선의무 전가, 중도해지 불리, 관리비·비용 전가, 계약갱신 제한, 담보·전세권 관련 등 8~12개. HUG 전세사기예방센터 유형 분류와 분쟁조정사례집 빈출 유형을 근거로 P1에서 확정.

## 6. 데이터 소스와 검증 가능성

완성된 "특약 + 위험 라벨" 공개 데이터셋은 존재하지 않는다(2026-07 조사 기준). 골든셋을 직접 구축하는 것이 이 프로젝트의 공개 기여물이다.

| 소스 | 검증 가능성 | 용도 | 제약 |
|---|---|---|---|
| 국가법령정보 Open API (법령·판례·해석례) | 최상 — 공식, ID 인용 | 라벨 근거, 리트리벌 코퍼스 | 특약 문구는 판례 본문에서 추출 |
| 주택임대차분쟁조정사례집 (국토부·법률구조공단·한국부동산원) | 최상 — 실제 분쟁+결과 | **골든셋 핵심 소스** (특약 문구·분쟁 결과 페어) | PDF 추출 수작업, 공공누리 유형 확인 |
| HUG 전세사기예방센터 사례·특약 가이드 | 높음 — 공식 | taxonomy 설계 근거 | 데이터셋 아닌 콘텐츠 |
| 국토부 표준임대차계약서 | 최상 | "특이사항 없음" 네거티브 샘플 | — |
| AI Hub 법률 데이터 (판례 라벨 6만+) | 높음 — 정부 구축 | 내부 학습·평가 보조 | **재배포 금지 → 공개 골든셋에 미포함** |
| LBox Open (판례 147k, NeurIPS 2022) | 높음 — 학술 검증 | 판례 코퍼스 보강, 평가 관행 참고 | 임대차 특화 아님 |
| 커뮤니티 특약 모음 (나무위키·블로그 등) | 낮음 — 출처 불명 | 문구 다양성 보강용만 | 라벨은 공식 근거로 재검증 후에만 부여 |

## 7. 골든셋 구축 계획

- 스키마: `조항 텍스트 → (카테고리, 발견 유형, 근거 문서 ID[])`. **근거 ID 없는 라벨 금지.**
- 규모: P1에서 30개(파일럿), P2에서 150~300개.
- 라벨링 원칙 (특약의 난점 4가지에 대한 대응):
  1. **실제 계약서 비공개** → 조정사례·판례 인용 문구를 1차 소스로, 커뮤니티 변형 문구로 다양성 보강, 실사용 단계에서 동의 기반 수집.
  2. **맥락 의존성** (같은 특약도 사실관계 따라 유효/무효) → 등급 판정 불채택의 근거. 라벨은 "상충 가능성 + 근거"까지만.
  3. **무한 변형** → 카테고리는 닫고 문구는 연다. 동일 라벨의 paraphrase 세트로 일반화 성능을 별도 측정.
  4. **비전문가 1인 라벨링** → 라벨링 기준 문서(`docs/labeling-guide.md`) 작성, 애매하면 "판단 불가" 클래스로 분리, 억지 라벨 금지.
- 완성 시 라벨링 기준 문서와 함께 공개(AI Hub 유래 데이터 제외). 라이선스는 소스별 공공누리 유형 확인 후 결정.

## 8. 평가 하네스 (3층)

1. **리트리벌**: 골든셋 조항별 정답 근거 문서 hit@k.
2. **분류·탐지**: 카테고리별 precision/recall/F1. 이 도메인은 **놓침(recall)이 오탐보다 치명적** — 임계값·튜닝 판단 기준으로 문서화.
3. **인용 충실도**: 생성된 설명이 인용 문서에 실제 근거하는지 LLM-as-judge.

프롬프트·모델·청킹·임베딩 변경 시 GitHub Actions에서 자동 실행, 기준선 대비 하락 시 실패. README에 지표 추이 기록.

## 9. 로드맵

| 단계 | 산출물 |
|---|---|
| P0 | 개인 레포 셋업, v1 파이프라인·데이터 이식, 팀 크레딧·라이선스 정리 |
| P1 | PDF → 조항 분해 → 분류 MVP, taxonomy 확정, 파일럿 골든셋 30개 |
| P2 | 골든셋 150+ 확장, 평가 하네스 3층 + CI 회귀 |
| P3 | 리포트 UI (Streamlit), 후속 Q&A 연결 |
| P4 | 배포 + 실사용자 확보, 골든셋·라벨링 기준 공개, (선택) 사진 OCR |

각 단계 종료 시 동작하는 데모가 하나씩 생기는 것을 원칙으로 한다.
